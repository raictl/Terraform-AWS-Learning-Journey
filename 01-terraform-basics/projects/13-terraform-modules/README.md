# Project 13 — Terraform Modules

## 📖 Overview

This project demonstrates how to use **Terraform Modules** to create reusable and maintainable infrastructure code.

Instead of writing the same Terraform configuration multiple times, we create a reusable child module and call it from the root module with different input values.

For this hands-on project, the Terraform **Local provider** is used so that the focus remains on understanding modules without requiring AWS infrastructure.

The project creates multiple environment-specific files using the same reusable module:

* Application
* Development
* Production
* QA

## 🧠 What is a Terraform Module?

A Terraform module is a collection of Terraform configuration files that are grouped together for reuse.

## 🏗️ Root Module vs Child Module

### Root Module

The root module is the Terraform configuration from which Terraform commands are executed.

Example:

```text
project-13-terraform-modules/
├── main.tf
├── variables.tf
├── outputs.tf
└── terraform.tfvars
```

The root module is responsible for:

* Configuring providers
* Calling child modules
* Providing input values
* Exposing useful outputs

### Child Module

The child module contains reusable Terraform configuration.

Example:

```text
modules/
└── application/
    ├── main.tf
    ├── variables.tf
    └── outputs.tf
```

# 📝 Implementation

## 1. Root Module Provider Configuration

The root module declares and configures the Local provider:

```hcl
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.0"
    }
  }
}

provider "local" {}
```

---

## 2. Reusable Child Module

The child module creates a local file:

```hcl
resource "local_file" "application" {
  filename = var.filename
  content  = var.content
}
```

The module doesn't hard-code the filename or content.

Instead, it receives them as variables.

---

## 3. Module Variables

The child module defines:

```hcl
variable "filename" {
  description = "Name of the application file"
  type        = string
}

variable "content" {
  description = "Content of the application file"
  type        = string
}
```

This makes the module reusable.

---

## 4. Module Output

The child module exposes the generated file path:

```hcl
output "file_path" {
  description = "Path of the application file"
  value       = local_file.application.filename
}
```

The root module can consume this output using:

```hcl
module.application.file_path
```

---

# 🔄 Calling the Module

The root module calls the reusable module:

```hcl
module "application" {
  source = "./modules/application"

  filename = var.application_filename
  content  = var.application_content
}
```

The same module is then reused for different environments.

### Development

```hcl
module "development" {
  source = "./modules/application"

  filename = "development.txt"
  content  = "Development environment"
}
```

### Production

```hcl
module "production" {
  source = "./modules/application"

  filename = "production.txt"
  content  = "Production environment"
}
```

### QA

```hcl
module "qa" {
  source = "./modules/application"

  filename = "qa.txt"
  content  = "QA environment"
}
```

The important part is that all environments use:

```hcl
source = "./modules/application"
```

Only the inputs change.

# 🔁 Module Reusability

One reusable module:

```text
modules/application
```

is used by:

```text
application
development
production
qa
```

Conceptually:

```text
                   application module
                         │
          ┌──────────────┼──────────────┐
          │              │              │
          ▼              ▼              ▼
     development     production        QA
          │              │              │
          ▼              ▼              ▼
 development.txt  production.txt     qa.txt
```

This eliminates duplicated infrastructure code.

# 📤 Root Module Outputs

The root module exposes outputs from the child modules:

```hcl
output "application_file" {
  description = "Application file created by the application module"
  value       = module.application.file_path
}

output "development_file" {
  description = "Development file created by the development module"
  value       = module.development.file_path
}

output "production_file" {
  description = "Production file created by the production module"
  value       = module.production.file_path
}

output "qa_file" {
  description = "QA file created by the QA module"
  value       = module.qa.file_path
}
```

This demonstrates how outputs can flow from:

```text
Resource
   ↓
Child Module Output
   ↓
Root Module Output
```

# 📦 Module Input Variables

The root module defines:

```hcl
variable "application_filename" {
  description = "Name of the application file"
  type        = string
  default     = "application.txt"
}

variable "application_content" {
  description = "Content of the application file"
  type        = string
  default     = "Hello from Terraform Module!"
}
```

The values can be provided through:

```text
terraform.tfvars
```

Example:

```hcl
application_filename = "application.txt"
application_content  = "Hello from Terraform Module!"
```

# 🔐 Provider Architecture

A key lesson from this project is the distinction between **provider configuration** and **provider dependency declaration**.

The root module configures the provider:

```hcl
provider "local" {}
```

The child module declares the provider dependency:

```hcl
terraform {
  required_providers {
    local = {
      source = "hashicorp/local"
    }
  }
}
```

In a reusable module architecture:

```text
Root Module
    │
    ├── Provider Configuration
    │
    ▼
Child Module
    │
    ├── Provider Dependency Declaration
    │
    ▼
Resources
```

# 💡 Best Practices

### 1. Build reusable modules

Avoid copying the same Terraform configuration for every environment.

Prefer:

```text
One reusable module
       ↓
Different inputs
```

---

### 2. Keep provider configuration in the root module

Configure providers in the root module and allow Terraform to pass the provider configuration to child modules.

---

### 3. Declare provider dependencies in reusable modules

Child modules should declare which providers they depend on using `required_providers`.

---

### 4. Use variables

Avoid unnecessary hard-coded values.

Instead of:

```hcl
filename = "application.txt"
```

use:

```hcl
filename = var.application_filename
```

---

### 5. Use outputs

Outputs make useful information available outside the module.

---

### 6. Keep modules focused

A module should generally have a clear purpose.

Examples:

```text
modules/
├── vpc/
├── security-group/
├── ec2/
├── iam/
└── application/
```

---

### 7. Never hard-code secrets

Don't put passwords, API keys, access keys, or other secrets directly into Terraform configuration or committed `.tfvars` files.
